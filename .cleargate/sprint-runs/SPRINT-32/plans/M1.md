## Per-story blueprint

### STORY-033-02 — Parallel-Spawn Ledger Attribution (RUN_ID barrier-writer)

**How this advances the sprint goal:** This is the hard prerequisite for parallel waves. Per-story token attribution is *already silently broken* under any sub-agent fan-out (live-confirmed in the STORY-033-01 spike: workflow agents fire `SubagentStop` against the orchestrator transcript with `delta=0/0`, mis-tagging every story's cost onto the prior ledger row). Making the three on-disk surfaces RUN_ID-aware is what lets STORY-033-04's barrier write one correct row per `(storyId, agent_type)` under concurrency. Without this, the parallel wave the rest of the sprint enables would report garbage cost data.

**Cross-story coupling:** None within M1 (disjoint from 032-01). DOWNSTREAM: this story *defines the contract* that STORY-033-04 (`launch_wave.mjs`, the barrier, the schema-typed `verdict.tokens`) consumes in M2. 033-02 builds NONE of the launcher — it makes the marker, sentinel, and `.session-totals.json` RUN_ID-aware and makes `token-ledger.sh` no-op on an already-written barrier row. The barrier itself, the `verdict` discriminated union, and the `RUN_ID` minting are STORY-033-04's surface (explicitly out of scope here per story §1.3).

**Schema changes (verbatim):**
- Dispatch-marker JSON (`write_dispatch.sh`) — add a `run_id` field when `RUN_ID` is set in the environment; omit it when unset. Resulting object:
  ```
  { work_item_id, agent_type, run_id?, spawned_at, session_id, writer }
  ```
- Ledger row (barrier-written by 033-04, schema *defined* here) — existing schema plus `run_id`; the `delta` for a barrier row equals the segment's `verdict.tokens` verbatim (no cross-row subtraction). Existing row schema confirmed at `.claude/hooks/token-ledger.sh:497-511`:
  ```
  { ts, sprint_id, story_id, work_item_id, agent_type, session_id, transcript,
    sentinel_started_at, delta_from_turn, delta, session_total, model, turns, run_id? }
  ```
- `.session-totals.json` — add RUN_ID-keyed entries alongside the existing `session_id`-keyed entries (different namespace; stale `session_id` keys coexist and age out — no migration). Existing per-session shape at `token-ledger.sh:484`:
  ```
  { input, output, cache_creation, cache_read, last_ts, last_turn_index }
  ```
- Sentinel filename (`pending-task-sentinel.sh`) — `.pending-task-${RUN_ID}.json` when `RUN_ID` is non-empty; fall back otherwise (see Gotchas for the exact fallback form).
- New story-frontmatter field `db_write_set: string[]` — **NOT this story** (EPIC-033 owns it; STORY-033-03 surfaces it). Do not add it here.

**Test scenarios (from §2.1 Gherkin — Developer/QA-Red must cover all 6):**

2. **`token-ledger.sh` no-op when a barrier row already exists** — given a barrier-written `run_id` row, a late `SubagentStop` for that segment's `work_item_id + run_id` detects the existing row, exits 0 without appending, logs the skip to the hook log.
3. **Dispatch marker carries the RUN_ID** — `write_dispatch.sh` with `RUN_ID` set writes a marker whose `run_id` equals it, still carrying `work_item_id`, `agent_type`, `session_id`.
4. **Sentinel keyed by RUN_ID, not TURN_INDEX alone** — two concurrent Task dispatches sharing one session + one TURN_INDEX but distinct RUN_IDs produce two distinct sentinel files; neither overwrites the other.
5. **Segment verdict missing `tokens` → ESCALATED, no row** — barrier marks the tokens-less segment ESCALATED and writes no ledger row for it; sibling GREEN segments' rows write normally. (NB: the *barrier* logic is 033-04; the assertion here is the boundary the no-op guard + re-key respect. QA-Red should test the on-disk invariant — no row is written for a RUN_ID that has no `tokens` — via the hook/script surfaces this story owns, not by building a barrier.)

### STORY-032-01 — TypeScript Skeleton Extractor + db_writes

**How this advances the sprint goal:** This is the net-new core of the code-map awareness layer. It produces the token-cheap structural index (exports, signatures, class members, type/interface decls, import edges) that lets the Architect plan from skeleton instead of re-grepping source, and it emits the per-module `db_writes` set that feeds EPIC-033's coarse DB collision axis (the fourth wave-compatibility predicate). It is the foundation both EPIC-032 (page rendering, 032-02/03) and EPIC-033 (DB-axis wave planning) build on — pure data, no rendering, no wiring.

**Cross-story coupling:** None within M1 (disjoint from 033-02). DOWNSTREAM: 032-01 emits *pure serializable data*; STORY-032-02 (page schema + git-SHA drift + 2k budget) and STORY-032-03 (wiki-build integration + index linking + Architect consumption) consume it in M2. This story writes NO markdown, NO frontmatter, NO files, and does NOT register anything in `cleargate wiki build` (all explicitly §1.3 out of scope). EPIC-033's `db_write_set` story-frontmatter field and the Architect SDR DB axis are owned by EPIC-033, NOT here — 032-01 only emits the per-module `db_writes` data.

**Schema changes (verbatim — these are the in-memory return types, no on-disk schema):**
- `scan-source.ts` exports: `discoverPackages(repoRoot): PackageRoot[]` and `walkSources(pkg): string[]`.
- `extract-skeleton.ts` exports: `extractSkeleton(pkg): ModuleSkeleton[]`.
- Per-module `db_writes` shape (verbatim from §1.2): `db_writes: { tables: string[]; schema_ddl: boolean }`.
- The skeleton per module records: (a) top-level `export` names, (b) exported function signatures (name + params + return type, no body), (c) exported class declarations with member names + visibility (`public`/`protected`/`private`), (d) exported `type`/`interface` declarations, (e) top-level `import` edges (specifier + bound symbol names). **Function/method bodies are never emitted.**

**Test scenarios (from §2.1 Gherkin — Developer/QA-Red must cover all 5):**
1. **Discover packages by tsconfig roots** — fixture with two dirs each having a `tsconfig.json`; both returned as package roots; no layout hardcoded in the result.
2. **Extract exported signatures without bodies** — module with a function, a class (public + private members), an interface; result lists the function signature, the class with member visibility, the interface; no body text anywhere.
3. **Detect drizzle writes against discovered `pgTable` vocabulary** — a schema module defining `users` via `pgTable` + a writer calling `db.insert(users)`; `db_writes.tables` for the writer contains `"users"`; the schema module has `schema_ddl: true`.
4. **Raw-SQL heuristic captures a literal table name** — module calling `pool.query("INSERT INTO sessions (id) VALUES ($1)")` → `db_writes.tables` contains `"sessions"`; a dynamically-built table name records the sentinel `"<dynamic>"`.
5. **A file with a syntax error is skipped and the build does not fail** — package whose src has one syntactically-broken file; an `Error` is logged to stderr naming the file; the offending symbol is skipped while other modules still produce skeletons; process exit code is 0.

Minimum counts (§4.1): 6 unit + 5 acceptance. `node:test` only (`*.node.test.ts` via `tsx --test`); vitest forbidden.

**§1.4 Open-decision defaults (recommended answers stand unless the Brief overrides):**
- **Nested tsconfig roots:** outermost `tsconfig.json` in a directory chain is the package root; nested configs that only narrow build options (no distinct `package.json`) fold into the parent; a nested dir with its own `package.json` is a distinct package.
- **Dynamic raw-SQL table name:** record the sentinel `"<dynamic>"` in `tables` (NOT nothing), so the EPIC-033 wave planner can apply fail-safe-serialize-on-unknown deterministically rather than mistaking "no writes" for "safe to parallelize."
