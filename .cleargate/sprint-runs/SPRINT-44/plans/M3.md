GOAL_RELATION: advances

**How it advances the goal:** the goal is "one local page where the owner sees every open work item, assembles the next sprint, and follows the running one". Today the Backlog and Plan tabs show only an item's id, title and badges. To judge an item while planning, the owner has to leave the page. STORY-062-05 lets them read the full ticket in the same modal the Sprint tab uses. It also lifts the POST-only Host check to every route, which closes the DNS-rebinding read hole STORY-062-04's post-flight found (flashcard 2026-11-10 #dashboard #security). That keeps Cross-Cutting Rule 7 true for the new read route. No Goal Acceptance Check changes. Check 3 (POST /plan without a token is 403) stays green because `planGuard` keeps every check after Host.

## CR:spec-clarification proposals (non-blocking; the plan states the decision taken)

None of these changes what the story asks for. The orchestrator can append them as one line to sprint-context `## Mid-Sprint Amendments`. Development does not need to wait for that.

1. **R3 / §1.5 / §3.2: "the Plan row's button goes outside the `<label>`."** Plan rows have no `<label>`. `cgPlanRowsHtml` (render.ts:617-627) emits a bare `<input type="checkbox" data-plan-id=…>` as a direct child of `<div class="plan-row">`, and no element wraps the row. **Decision:** the view button is a sibling inside `.plan-row`, placed as the row's last child. The requirement is then met by construction: the button is not a `<label>` descendant and not the checkbox. The plan also forbids adding a `<label>` to the row.
2. **R4: the `<error>` text is undefined when the response has no JSON `error`, or when the request never reaches the server.** **Decision:** use `body.error` when it is a non-empty string. Otherwise use `HTTP <status>`. A rejected or throwing `fetch` gives `server unreachable`, the same word `cgPlanResultHtml` uses (render.ts:653). Example: `BUG-106 could not be loaded: server unreachable`.
3. **R1 `title` vs R4 modal title.** These do not conflict. The modal title is the id (R4, and the same as story/epic modals at render.ts:848/850). The response's `title` is the backlog item's title (R1). It is carried in the response, and the client does not use it.
4. **§3.3 lists only 200/404/403 for `/doc`.** Two Architect additions, both JSON `{ ok:false, error }`:
   - `500 "cannot read <item.file>"` when the listed file cannot be read.
   - `500 "internal error: <msg>"` when a collector throws. This is Rule 6: an uncaught throw inside the `http` request listener would crash the daemon.

   `/doc` answers only `GET`. Any other method on `/doc` falls through to the existing 404, after the Host guard has run.

  ```ts

   * STORY-062-05 R1/R2: GET /doc?id=<ID> — one backlog-listed item's body, rendered and capped.
   * The query id is only ever compared with collectBacklog ids; the file read is the matched item's own `file`.
   */
  function handleDocGet(
    res: http.ServerResponse,
    url: string,
    cwd: string,
    collectBacklogFn: (cwd: string) => BacklogData,
  ): void {
    let id = '';
    try {
      id = new URL(url, 'http://127.0.0.1').searchParams.get('id') ?? '';
    } catch {
      id = '';
    }
    const item = id === '' ? undefined : collectBacklogFn(cwd).items.find((i) => i.id === id);
    if (item === undefined) {
      sendJson(res, 404, { ok: false, error: 'unknown id' });
      return;
    }
    let raw: string;
    try {
      raw = fs.readFileSync(path.join(cwd, item.file), 'utf8');
    } catch {
      sendJson(res, 500, { ok: false, error: `cannot read ${item.file}` });
      return;
    }
    sendJson(res, 200, { ok: true, id: item.id, title: item.title, html: renderMarkdown(capDoc(raw)) });
  }
  ```
