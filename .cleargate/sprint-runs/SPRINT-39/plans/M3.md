## NORMATIVE RULINGS — bind both items, supersede the item text where they conflict

### N1 — The recorded premise "`$` under `/m` does not match before a `\r`" is FALSE in JavaScript. Measured.

BUG-043's Q2 human decision carries this rider:

> *"New failure mode this introduces, and it must be handled: `$` under the `m` flag does not match
> before a `\r`, so a CRLF-converted `CLAUDE.md` — or a marker line with trailing whitespace —
> silently stops matching… the fix must normalise line endings and trim trailing whitespace on the
> marker line before matching, and the test suite must cover a CRLF fixture."*

**The CRLF half of that is wrong.** In ECMAScript, `LineTerminator` includes U+000D CARRIAGE
RETURN, so `^` and `$` under `/m` are CRLF-safe. Proven directly:

```
/^b$/m.test("a\r\nb\r\nc")  ->  true
/^b$/m.test("a\rb\rc")      ->  true
```

and confirmed end-to-end: a strict `/^<!-- CLEARGATE:START -->$([\s\S]*)^<!-- CLEARGATE:END -->$/m`
returns `"\r\nBLOCK\r\n"` — a correct match — on a fully CRLF fixture. The premise is true of
Python's `re.MULTILINE` and of several other engines; it is not true here.

**The trailing-whitespace half IS real.** A marker line with trailing spaces returns `null` under a
strict anchor.

**Consequence — and this matters, because the literal instruction is destructive.** "Normalise line
endings before matching" is only implementable as *whole-file* normalisation, and the write path
(`writeBlock` / `removeBlock` / `injectClaudeMd`) operates on the same string it matched. So a
literal implementation rewrites a CRLF user file to LF wholesale — a silent, whole-file content
change to a file the user owns, which is the precise harm class BUG-043 exists to close. Rejected.

**RULING: tolerance goes in the pattern, not in a mutation of the file.** This delivers the decision's
stated outcome (CRLF and trailing-whitespace files keep matching) with zero bytes rewritten. The
CRLF fixture the decision asks for is still required — it now pins that CRLF was never broken,
which is worth having. Listed in `## Open decisions` as reversible by the human; not blocking.

### N2 — The two regexes, verbatim. Copy; do not paraphrase.

`cleargate-cli/src/lib/claude-md-surgery.ts:7` becomes:

```ts
const BLOCK_REGEX = /^<!-- CLEARGATE:START -->[ \t]*$([\s\S]*)^<!-- CLEARGATE:END -->[ \t]*$/m;
```

`cleargate-cli/src/init/inject-claude-md.ts:18` becomes (no capture group — matches its current shape):

```ts
const BLOCK_REGEX = /^<!-- CLEARGATE:START -->[ \t]*$[\s\S]*^<!-- CLEARGATE:END -->[ \t]*$/m;
```

Greedy `[\s\S]*` is **retained** per the Q2 human decision. `[ \t]*` is horizontal whitespace only —
never `\s*`, which would swallow newlines and re-open the very span the anchor exists to bound.
Never `\r?$` — `$` already handles `\r` (N1), and consuming the `\r` corrupts the captured body
(measured: `\r?$` returned `"\nBLOCK\r\n"` where today returns `"\r\nBLOCK\r\n"`).

### N3 — The `includes()` guards diverge from the anchored regex and produce a SILENT NO-OP. This is the fix's real hazard, and neither `§4` nor its amendment names it.

`writeBlock` (`claude-md-surgery.ts:25-31`) and `removeBlock` (`:39-45`) guard with
`content.includes(CLEARGATE_START)` / `includes(CLEARGATE_END)` — **substring** checks — and then
call `content.replace(BLOCK_REGEX, …)`. Today the two agree, because the regex is itself
substring-shaped. **Under anchoring they diverge**, and `String.replace` with a non-matching regex
returns the original string. Measured:

| fixture | `writeBlock` today | `writeBlock` anchored, guards left as `includes` |
|---|---|---|
| `A` block alone on its lines | changed | changed |
| `C` marker with trailing spaces | changed | **NO-OP, silent** |
| `D` markers only quoted inline in prose | changed | **NO-OP, silent** |
| `G` markers indented 2 spaces | changed | **NO-OP, silent** |
| `F` no markers at all | throws | throws |

`removeBlock` is identical. The downstream consequence is worse than the function's own return
value: `uninstall.ts:437` does `const stripped = removeBlock(claudeMdContent); await
writeAtomic(claudeMdPath, stripped);` then pushes `'CLAUDE.md (CLEARGATE block)'` onto
`removedPaths`. A silent no-op therefore **writes the file back unchanged and reports the block as
removed.**

**RULING: add a third guard, keyed on the regex, after the two existing `includes` guards, in both
`writeBlock` and `removeBlock`:**

```ts
const NOT_ANCHORED =
  'CLAUDE.md has CLEARGATE markers but no anchored block (both markers must sit alone on their own line)';
…
  if (!BLOCK_REGEX.test(content)) {
    throw new Error(NOT_ANCHORED);
  }
```

**The two existing `includes` guards and their exact messages stay, in their current order.** That
is not stylistic: three existing tests assert those two message strings verbatim
(`test/lib/claude-md-surgery.node.test.ts:168`, `:175`, `:204`). Unifying them into one message reds
all three for no gain. Additive is both correct and free.

`uninstall.ts:332-337` carries its own duplicate pair of `includes` guards. Leave them: they run
*before* classification and their job is to abort early on a file with no markers at all. With N3's
third guard in place, the unanchored case now surfaces at `:441` as
`Warning: could not strip CLAUDE.md block: <NOT_ANCHORED>` and the file is left untouched — loud,
not silent. **This is what makes BUG-043 `§4`'s "uninstall.ts inherits the regex fix for free; no
separate change" true.** Without N3 that line is false. It is conditionally correct, and the
condition is N3.

### N8 — Export a matcher, not the regex.

To let the test import the grammar without exporting a mutable `RegExp` (`/m` regexes are stateless
here — no `/g` — but exporting the object invites `.lastIndex` misuse and in-place edits), export a
predicate from `claude-md-surgery.ts`:

```ts
/** True when the file carries a well-formed block: both markers alone on their own lines. */
export function hasAnchoredBlock(content: string): boolean {
  return BLOCK_REGEX.test(content);
}
```

`init.node.test.ts` scenario 2 uses `hasAnchoredBlock` plus `removeBlock` in place of its private
regex. CR-105 uses it in wave9 to express "exactly one anchored block" (N9). `uninstall.ts` may
adopt it for its `:332-337` pre-check, but is not required to.

### N9 — "Exactly one block in the file" MUST be counted on ANCHORED MARKER LINES, never on substring occurrences.

CR-105 `§4` requires *"exactly one block in the file."* A naive
`content.split(CLEARGATE_START).length - 1 === 1` **fails on the block ClearGate itself ships**.
Measured, both trees:

```
root CLAUDE.md      : anchored START [129]  anchored END [186]  inline-mention line [178]
canonical CLAUDE.md : anchored START [7]    anchored END [64]   inline-mention line [56]
```

Line 178 (root) / 56 (canonical) is the block's own sentence *"Content OUTSIDE this
`<!-- CLEARGATE:START -->…<!-- CLEARGATE:END -->` block takes precedence…"*, which sits **inside**
the block and must keep doing so. Every installed repo therefore has two `START` substrings and two
`END` substrings and always will. The count that means anything is:

```ts
const anchoredStarts = content.split('\n').filter(l => /^<!-- CLEARGATE:START -->[ \t]*$/.test(l)).length;
```

The same trap bites BUG-043's `§5` Defect-B assertion *"no user line is fused onto a marker"*. Express
it as: the output contains the exact string `I documented the `, **and** `anchoredStarts === 1`,
**and** `anchoredEnds === 1`.

### N10 — Anchoring narrows Defect B; it does not eliminate it. Pin the residual as KNOWN, or it gets rediscovered.

Measured:

| fixture | today | anchored (N2) |
|---|---|---|
| `E` stray `END` quoted **inline** in prose below the block | eats `I documented the ` | **fixed** — body is `"\nBLOCK\n"` |
| `H` stray `END` **alone on its own line** below the block | eats `user line one` | **still eats it** |

Greedy plus anchored means the match still runs to the **last anchored** `END`. A user who writes a
bare `<!-- CLEARGATE:END -->` on its own line below the block still loses the text between. That is
the accepted consequence of the Q2 decision to retain greedy, and it is correct — non-greedy would
truncate the real block at line 178. **BUG-043 must ship `H` as an explicitly-titled
known-limitation test** (`documents the residual: a stray END alone on its own line still extends
the greedy match`), asserting the current behaviour. Silence here is how it gets refiled in six
months as a new bug.

## Question 1 — Does BUG-043's fix change `doctor`'s drift behaviour?

**Answer: it is a FIX, with zero regressions. Measured end-to-end through `checkCanonicalDrift`, not
reasoned from `readBlock`.**

Method: three out-of-tree copies of `drift-check.ts` were built, each importing a different copy of
`claude-md-surgery.ts` — today's, strict-anchored (`/^…$/m`, no tolerance), and the N2 tolerant
anchor. Each was run against seven tmpdir fixtures with a fixed canonical `CLAUDE.md` and a varying
root `CLAUDE.md`. `DRIFT reported` means `checkCanonicalDrift(tmp).drifted` contains
`{path:'CLAUDE.md', reason:'claude-md-block-mismatch'}`.

| root `CLAUDE.md` fixture | today | strict-anchored | **N2 tolerant** |
|---|---|---|---|
| LF, block mid-file (today's real shape) | clean | clean | clean |
| LF, block **at top** (post-CR-105 shape) | clean | clean | clean |
| **CRLF** throughout | clean | clean | clean |
| marker line with **trailing spaces** | **DRIFT** | **DRIFT** | **clean** |
| markers **indented** 2 spaces | DRIFT | DRIFT | DRIFT |
| block body genuinely diverged | DRIFT | DRIFT | DRIFT |
| no block at all | DRIFT | DRIFT | DRIFT |

Three findings:

1. **CRLF is a non-event.** All three variants report clean. The recorded premise that anchoring
   breaks CRLF is false (N1), so the mitigation it demanded — normalise-before-match — is
   unnecessary, and implementing it literally would have been actively harmful (it rewrites the
   user's file).
2. **The only row that moves is trailing-whitespace, and it moves from a FALSE POSITIVE to CLEAN.**
   Today's greedy `readBlock` captures the trailing spaces *into* the block body, so
   `hashNormalized(rootBlock) !== hashNormalized(canonicalBlock)` and `doctor` reports drift on a
   file whose block is materially identical. `hashNormalized` (`sha256.ts:32`) normalises CRLF but
   not marker-line trailing whitespace, so today's behaviour here is simply wrong. N2's `[ \t]*`
   fixes it.
3. **Everything that should report drift still does.** Indented markers, a genuinely diverged body,
   and an absent block are all unchanged.

**Ruling: a fix, and a note is warranted but not a caveat.** The Dev report should state
"`cleargate doctor` stops reporting a false `claude-md-block-mismatch` on a `CLAUDE.md` whose marker
line carries trailing whitespace; all other drift verdicts are byte-identical." Two corrections
belong in the same sentence: the command is bare `cleargate doctor`, not `doctor --drift` (N6), and
the guard is meta-repo-only (`drift-check.ts:145-148`) so no end-user install is affected.

**Had the fix shipped strict-anchored with no `[ \t]*` tolerance, it would still not have been a
drift regression** — the strict column matches today's column on all seven rows. The `[ \t]*` earns
its place elsewhere: in `writeBlock`/`removeBlock`, where strict-anchoring alone produces the silent
no-op of N3. That distinction is worth carrying, because it means the tolerance is a
*correctness* requirement for the surgery functions, not a *compatibility* requirement for drift.
