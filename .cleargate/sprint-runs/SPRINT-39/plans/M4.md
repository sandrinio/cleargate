## §Q5-B — CR-105 post-flight §Q5.3 resolved: the CR-110 vocabulary question

**RULING: in scope, but NOT as CR-110's §1 would have it — the two vocabularies are on different
axes and must stay separate.**

The post-flight is right that `met | partial | missed` has no slot for M3, and M4 is about to be a
second instance across all eight items. But widening the **sprint verdict** with a **milestone
relation** would be a category error:

- `met | partial | missed | not-mechanically-verifiable` answers *"was the sprint's goal
  achieved, and could that be checked mechanically?"* — one verdict, one per sprint.
- `advances | off critical path` answers *"does this unit of work relate to the goal at all?"* —
  one relation, one per milestone, N per sprint.

A sprint whose goal is `met` can contain milestones that are `off critical path`. SPRINT-39 is
exactly that. Folding the second into the first would force the Reporter to score the *sprint*
`partial` because a *milestone* was unrelated — manufacturing precisely the linkage O5 forbade.

**Therefore CR-110 ships two things, not one:**

1. The sprint verdict vocabulary stays `met | partial | missed`, plus CR-110's own
   `not-mechanically-verifiable` for the check itself. Sites: canonical `SKILL.md` §0.5 touchpoint
   5, §E.2's Brief line, §E.2's 🎯 note.
2. A **new, separate, per-milestone** line: `GOAL_RELATION: advances | off critical path`, emitted
   by the Architect in each milestone plan and quoted by the Reporter in §1. Site: `reporter.md`

### Source change — the lock, and the two things that will be got wrong

Human decision (§Open Questions): **lockfile**, not a shard. The shard is CR-106's.

**Shape:**

```
lockPath  = `${stateFile}.lock`
acquire   = fs.openSync(lockPath, 'wx')     // O_CREAT|O_EXCL|O_WRONLY — atomic create-or-EEXIST
payload   = JSON.stringify({ pid: process.pid, at: new Date().toISOString() })
release   = fs.unlinkSync(lockPath)
```

`'wx'` is the load-bearing flag. `'w'` truncates-or-creates and provides no exclusion.

**GOTCHA 1 — `process.exit()` does NOT run `finally`. A `finally`-only release leaks the lock on
the most common path in the file.** `update_state.mjs` calls `process.exit()` **thirteen** times:
`:42` (usage), `:94`, `:102`, `:110`, `:130`, `:135`, `:146`, `:166`, `:184`, `:201`, `:223`, and —
critically — **`:229`, the idempotency no-op**, which is the single most frequently taken exit in
normal operation (`No-op: <id> is already in state "<state>"`). Node's `process.exit()` emits the
`'exit'` event and then calls `reallyExit`; it does **not** unwind the stack, so `finally` blocks do
not run. Release MUST be registered as `process.on('exit', () => { try { fs.unlinkSync(lockPath) }
catch {} })`, installed immediately after a successful acquire. A `finally` block alone ships a
tool that self-deadlocks on its second no-op.

**GOTCHA 2 — the read at `:99` and BOTH migration writes must be inside the critical section.**
`:99` is the read half of the race. But `:114-117` (`migrateV1ToV2` + `atomicWrite`) and `:120-123`
(`migrateStateToV3` + `atomicWrite`) are **two more full-document writes that happen before the
action dispatch**. A lock that wraps only the action-branch `atomicWrite` calls (`:155`, `:176`,
`:193`, `:210`, `:241`) leaves two unguarded writers. The critical section is `:97` through the end
of `main()` — acquire immediately after `resolveStateFile()` (`:90`) and the `existsSync` guard
(`:92-95`), which is before the first read.

**GOTCHA 3 — no synchronous sleep exists in Node's fs API.** The retry spin needs
`Atomics.wait(new Int32Array(new SharedArrayBuffer(4)), 0, 0, ms)` — the standard synchronous
sleep. `setTimeout` is unusable: `main()` is synchronous top-to-bottom (`:246`).

**Stale-lock policy (§2 edge condition 3, §5 case 4).** Two independent gates, both required:
- **Liveness:** read `pid` from the lock payload; `process.kill(pid, 0)` throws `ESRCH` when the
  process is gone → steal. Note it throws `EPERM` when the process exists but is owned by another
  user — **`EPERM` means alive, do not steal.**
- **Age ceiling:** a lock older than a fixed budget is stealable regardless. Pick a value and state
  it in the code comment; a bare liveness check fails when the pid has been recycled.

**Single-invocation performance (§2 edge condition 3).** One `openSync` + one `unlinkSync` per run.
Do not add a `statSync` on the happy path.

### OD-3 — `cleargate new <type>` does NOT strip `<instructions>` blocks. Ruled: **no stripping.**

Measured directly, not inferred:

- Eight of ten templates carry exactly one `<instructions>` block (`Bug.md`, `CR.md`,
  `Sprint Plan Template.md`, `epic.md`, `hotfix.md`, `initiative.md`, `spike.md`, `story.md`);
  `sprint_context.md` and `sprint_report.md` carry none. **`hotfix.md` is in the carrying set.**
- The shipping renderer strips nothing. `hotfixNewHandler` reads the template and performs
  exactly three substitutions — `cleargate-cli/src/commands/hotfix.ts:188-191`:
  `.replace(/\{ID\}/g, idStr).replace(/\{SLUG\}/g, opts.slug).replace(/\{ISO\}/g, now)`.
  `grep -n 'instructions' src/commands/hotfix.ts` returns **nothing**.
- The one real scaffolded artefact, `archive/HOTFIX-001_init_skip_strips_exec_bit.md`, carries
  **zero** `<instructions>` blocks while its own template carries one. Since the renderer cannot
  have removed it, **it was hand-cleaned after scaffolding.** That is the actual current workflow,
  and it is a human editorial step, not a renderer behaviour.

**Ruling — three reasons, in order of weight:**

1. **CR-108 §4 case 7 demands `cleargate new hotfix` be byte-identical to today's `hotfix new`.**
   Stripping violates that by construction: `hotfix.md` carries a block, so a stripping renderer
   cannot reproduce the current output. The two requirements are mutually exclusive as written, and
   byte-identical regression is the one that protects a command that already ships to users.
2. **The block is the drafting agent's contract.** Every work-item template's `<instructions>`
   block is what tells the agent to render a Brief and halt — the universal pre-push handshake in
   CLAUDE.md. Removing it at scaffold time deletes the instruction from the artefact the agent
   subsequently reads.
3. **Stripping is separable.** If hand-cleaning proves a real burden across nine types, it is its
   own CR with its own regression case. It is not a precondition of "one scaffolder for every type",
   and folding it in would make case 7 unverifiable.

CR-108's Developer implements substitution-only rendering, matching `hotfix.ts:188-191`. Any
`<instructions>` handling is **out of scope** and a kick-back if it appears.
