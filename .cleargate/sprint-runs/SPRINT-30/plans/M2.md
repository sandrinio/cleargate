## §2 Wave Plan

The sprint plan §2.1 said:
> "Wave 3 (mixed): CR-070 + CR-071. CR-070's story sequence runs sequentially (shared knowledge-doc + CLAUDE.md). CR-071's protocol-doc anchor story runs in parallel with CR-070's first story (disjoint files); CR-071's agent-propagation story serializes after CR-070's CLAUDE.md edit (both touch `cleargate-planning/.claude/` tree)."

**Reconciliation.** Each CR decomposed to a SINGLE story (STORY-070-01, STORY-071-01) — not the multi-story sequence the sprint plan §2.1 anticipated. So the "parallel with the first story / serial with the second" framing collapses. The question becomes: are STORY-070-01 and STORY-071-01 parallel-eligible or sequential?

Sprint plan §2.2's Merge Ordering table is authoritative on this: it lists `cleargate-planning/CLAUDE.md (canonical) + payload mirror + live` as touched by BOTH CR-070 and CR-071, with merge order **CR-070 → CR-071** and rationale *"CR-070 removes `**Sprint mode.**` paragraph; CR-071 may add a one-line autonomy pointer. Land 070 first so 071's pointer doesn't reference a paragraph mid-deletion."*

**Verification by grep.** STORY-070-01 §3.1 lists `cleargate-planning/CLAUDE.md` in its Doc Files row. STORY-071-01 §3.1 does NOT list `cleargate-planning/CLAUDE.md` directly — it touches `cleargate-planning/.claude/agents/*.md`, `cleargate-planning/.claude/skills/sprint-execution/SKILL.md`, `cleargate-planning/.claude/hooks/pre-tool-use-autonomy.sh`, `cleargate-planning/.claude/settings.json`, and `.cleargate/knowledge/cleargate-protocol.md`.

**Result:** STORY-071-01 as currently drafted does NOT touch `cleargate-planning/CLAUDE.md`. So the sprint plan §2.2 anticipated overlap is actually absent in the story-level decomposition. **BUT** both stories DO share the `cleargate-planning/.claude/` tree (071 edits agents + skills + hooks + settings; 070 edits the canonical CLAUDE.md sibling). The npm payload mirror via `npm run prebuild` from `cleargate-cli/` runs over the WHOLE `cleargate-planning/.claude/` tree at once — concurrent worktrees both calling `npm run prebuild` race on the payload directory write.

**Decision: serialize.** Reasons (in priority order):

1. **Conservative interpretation of sprint plan §2.2.** The plan ordered `CR-070 → CR-071` for a reason; even if the direct CLAUDE.md overlap has dissolved at decomposition, three-site dogfood-mirror discipline still applies across the whole `.claude/` tree. Running concurrently means two `npm run prebuild` invocations could clobber each other's payload writes (FLASHCARD `#wiki #protocol #mirror` 2026-04-19: "Subagent .md files ship in BOTH cleargate-planning AND cleargate-cli/templates/" — the prebuild copy is a directory-tree operation, not per-file).
2. **Live re-sync is manual and once-per-merge.** Both stories list `cleargate init` re-run against meta-repo as a DoD item. Running both stories in flight at once and re-running `cleargate init` after each merge means the second merge potentially blows away the first's hand-port if a manual edit was needed (it isn't, but the cognitive overhead of two interleaved re-syncs is higher than serial).
3. **CR-070 retires `**Sprint mode.**` paragraph from canonical CLAUDE.md.** CR-071 may later choose to add a cross-reference pointing to the new protocol §22. If 071 lands first and decides to add such a pointer, the pointer reference becomes the wrong line number after 070 deletes the Sprint-mode paragraph. Trivially fixable but adds rebase noise.
