# CR-099: The Dogfood Split Does Not Match What CLAUDE.md Says It Is

## 0.5 Open Questions

> Filed as a **finding**. Both items are small, but each is a place where the
> documented model and the repo disagree, and that gap is what let a stale hook
> run for an unknown period.

- **Question:** Should `.claude/hooks/token-ledger.sh` be untracked (`git rm --cached`) to match the `/.claude/` gitignore, or should the ignore rule be narrowed to admit it deliberately?
- **Recommended:** Untrack it. `.gitignore`'s own comment says the runtime instance "is not team-shared; canonical definitions live in `cleargate-planning/.claude/` and ARE tracked". One file contradicting that is an accident of ordering, not a decision. Untracking changes what teammates receive on pull, so it is a human call.
- **Human decision:** **Untracked**, per the recommendation, under the session-wide "fix remaining issues" instruction. `git rm --cached` only — the working file is untouched and the live hook keeps running. `git ls-files .claude/` now returns 0.

  **Stated out loud, as §2 asks:** a `git pull` will now *delete* `.claude/hooks/token-ledger.sh` from any other checkout that has it. That is the correct end state — the live instance is per-machine — but it is a visible change. Recovery on any affected checkout is `cleargate init`, which rewrites the whole live instance from the payload.

- **Question:** Is the npm payload supposed to be tracked?
- **Recommended:** Leave it untracked and fix the documentation. `prebuild` regenerates it from canonical on every build and `prepublishOnly` self-builds, so tracking it would only create merge noise and a second source of truth. The defect is the claim, not the state.
- **Human decision:** **Left untracked; the documentation was the defect.** Confirmed by measurement: `git ls-files templates/cleargate-planning/` returns 0, and `git check-ignore -v` names `.gitignore:5` as the rule. CLAUDE.md now calls it "NPM payload (generated, gitignored)" and says explicitly that it is a build artifact, not a second source of truth.

## 1. The Context Override (Old vs. New)

**Obsolete Logic (What to Remove / Forget):**
- Forget that `/.claude/**` is uniformly gitignored in the meta-repo. Exactly one file under it is tracked, and `.gitignore` has no effect on already-tracked files.
- Forget that the npm payload is tracked. CLAUDE.md says "**NPM payload (tracked, auto-mirrored):** `cleargate-cli/templates/cleargate-planning/.claude/**`". `git ls-files` returns nothing for that path — it is gitignored in the `cleargate-cli` repo and regenerated by `prebuild`.

**New Logic (The New Truth):**
- `/.claude/**` is uniformly gitignored **and uniformly untracked**. `git ls-files .claude/` returns 0, with no exceptions. Machine-checked, not honour-system.
- The npm payload is a **generated, gitignored build artifact**, regenerated from canonical by `npm run prebuild` and again by `prepublishOnly`. It is never a source of truth and is never hand-edited.
- Canonical (`cleargate-planning/.claude/**`) is the only tracked copy, and remains the only place edits land.

**Why it matters.** The dogfood split has bitten before: CLAUDE.md records that BUG-024 "shipped its own fix while still running with the buggy hook" because canonical was edited and the live instance never re-synced. The same shape recurred in this session — `.claude/hooks/token-ledger.sh` was tracked *and* stale, so the repo was about to ship the `[[CR-097]]` attribution fix while executing the pre-fix hook. It was caught only because `git status` showed the file as modified, which happens for exactly one of the nine live hooks.

A second, quieter consequence: because that one file is tracked, every developer's local edits to it appear as repo changes, and a `cleargate init` re-sync silently rewrites a tracked file.

**Measured drift in this repo (2026-08-01).** Comparing all 11 live agents against canonical, four are stale — and canonical is newer in every case, so the live instance is running outdated instructions:

| Agent | Differing lines | What live is missing |
|---|---|---|
| `qa` | 22 | Test-file naming still hardcoded to `*.red.node.test.ts`; canonical reads it from `sprint_context.md` §Test Stack. Also missing the TPV wiring-soundness rules. |
| `devops` | 6 | Stale `v2 standard lane` vocabulary that canonical has already dropped. |
| `cleargate-wiki-ingest` | 3 | The entire §21.2 bucket-allowlist behaviour, and the `INITIATIVE-` bucket row. |
| `cleargate-wiki-lint` | 2 | Frontmatter description quoting only — cosmetic. |

The `qa` and `cleargate-wiki-ingest` gaps are behavioural, not cosmetic: a sprint run today would use the stale test-naming rule and would ingest buckets the config excludes. Nothing surfaces this — there is no drift check for the live instance, which is the general form of the problem this CR describes. `cleargate doctor` has a drift guard for *installed* files, but the meta-repo's live `/.claude/` is not an install.

**Re-measured and resolved 2026-08-01.** All four agents above were still stale, and the hooks had drifted too. The live instance has been re-synced from canonical (hooks rendered with the version pin, agents copied verbatim); `diff` across all 11 agents and all 9 hooks is now clean.

Two findings from the re-sync that the original measurement did not cover:

| File | Drift | Verdict |
|---|---|---|
| `hooks/pre-tool-use-autonomy.sh` | live read `.agent`; canonical reads `.agent_type` | **Live was wrong.** Every dispatch marker ever written — checked across all `.dispatch-*.json` in `sprint-runs/`, from `write_dispatch.sh@cleargate-0.9.0` through `@0.15.0` — carries `agent_type` and never `agent`. The live hook was reading a field that has never existed, so its agent lookup always fell through to `"unknown"`. |
| `hooks/stamp-and-gate.sh` | `cleargate-pin: 0.10.0` vs `__CLEARGATE_VERSION__` | **Not drift** — expected pin substitution. But the pin was 10 minor versions behind the installed 0.20.0. Re-render corrected it. |

The first is the clearest evidence for this CR's thesis: a live hook silently read a non-existent field for an unknown period, and nothing anywhere reported it. It was found only because this CR's re-sync forced a file-by-file comparison.

**Still open (deliberately not in scope):** there is no automated live-instance drift check. `cleargate doctor`'s drift guard covers *installed* scaffolds; the meta-repo's live `/.claude/` is not an install, so it remains unguarded. The regression test added here locks the *tracking* rules, not content parity. A `doctor` check comparing live against `cleargate-planning/` in the meta-repo would be the general fix and deserves its own item.
